# TaskBridge
### تحويل طلبات العمل غير الواضحة إلى خطط عملية قابلة للتنفيذ

**Turn Unclear Requests into Clear, Actionable Plans.**

---

## 1. نظرة عامة على المشروع

**TaskBridge** هو تطبيق ويب متجاوب يساعد المستقلين والخريجين الجدد والمهنيين في بداية مسيرتهم على تحويل أهدافهم وطلبات العمل غير الواضحة إلى خطط منظمة تتضمن مهامًا محددة وأولويات واضحة وخطوات قابلة للتنفيذ.

يستطيع المستخدم إنشاء خطة، وتحديد النتيجة التي يريد الوصول إليها، وإضافة المهام اللازمة، وتحديد أولوياتها وحالات تنفيذها، ثم متابعة التقدم من خلال واجهة واحدة.

يُبنى المشروع باستخدام **Lovable** بوصفه أداة AI App Builder، و**Supabase** لإدارة المصادقة وقاعدة البيانات والتحكم في الوصول إلى البيانات.

### المبدأ الأساسي

> **Build the System, Not the Screen.**
>
> ابنِ النظام، لا الواجهة فقط.

لا يقتصر الهدف على بناء واجهة جذابة، بل يشمل فهم النظام الذي يقف خلفها، وتصميم بياناته، وتحديد سلوكه، والتحقق من وظائفه وأمانه.

## 2. المشكلة والحل

### 2.1 المشكلة — Problem

قد يعرف الشخص ما يريد تحقيقه، لكنه لا يعرف كيف يحوّل هدفه إلى خطوات عملية.

قد يواجه أسئلة مثل:

- ما النتيجة التي يجب الوصول إليها؟
- ما المهام المطلوبة لتحقيقها؟
- ما المهام التي يجب البدء بها؟
- ما الذي أُنجز بالفعل؟
- ما الذي لا يزال قيد التنفيذ؟
- ما الخطوة التالية؟

غياب خطة واضحة قد يؤدي إلى صعوبة تنظيم العمل وتحديد الأولويات ومتابعة الإنجاز.

### 2.2 الحل — Solution

يوفر TaskBridge مساحة منظمة لإدارة الخطط والمهام، بحيث يستطيع المستخدم تحويل هدفه إلى خطوات واضحة ومتابعة تنفيذها.

تعتمد الفكرة على التسلسل التالي:

**Goal → Plan → Tasks → Priorities → Status → Progress**

| المفهوم | وظيفته |
|---|---|
| Goal | تحديد الهدف المراد تحقيقه |
| Plan | تنظيم العمل المطلوب |
| Tasks | تقسيم العمل إلى مهام |
| Priorities | تحديد أهمية كل مهمة |
| Status | متابعة حالة تنفيذ المهمة |
| Progress | قياس التقدم في الخطة |

## 3. الفئة المستهدفة

صُمّم التطبيق بصورة أساسية لخدمة:

- **Freelancers:** المستقلين الذين يديرون طلبات العملاء ومشروعاتهم.
- **Recent Graduates:** الخريجين الجدد الذين ينظمون مشروعاتهم المهنية.
- **Early-Career Professionals:** المهنيين في بداية مسيرتهم العملية.
- **Individual Users:** الأفراد الذين يحتاجون إلى تنظيم أهدافهم وتحويلها إلى مهام قابلة للتنفيذ.

تركز النسخة الأولى على الاستخدام الفردي، ولا تتضمن التعاون بين عدة مستخدمين داخل الخطة نفسها.

## 4. سيناريو استخدام عملي

لنفترض أن مستقلًا يريد إطلاق متجر إلكتروني صغير، لكنه لا يعرف كيف ينظم العمل المطلوب.

يمكنه إنشاء خطة داخل TaskBridge، وتحديد النتيجة المستهدفة، ثم إضافة المهام اللازمة لتحقيقها.

### معلومات الخطة

**Plan Title:** Launch a Small Online Store

**Description:** تجهيز متجر إلكتروني صغير لعرض المنتجات وبيعها.

**Desired Outcome:** إنشاء متجر إلكتروني يعمل بصورة مناسبة، ويتيح للعملاء استعراض المنتجات والتواصل مع صاحب المتجر.

**Deadline:** موعد نهائي اختياري.

### المهام

| المهمة | Priority | Status |
|---|---|---|
| تحديد متطلبات الموقع | High | Done |
| تنظيم معلومات المنتجات | High | In Progress |
| تصميم واجهة الموقع | High | To Do |
| إضافة معلومات التواصل | Medium | To Do |
| مراجعة النسخة الأولى | Medium | To Do |

عندما يحدّث المستخدم حالة إحدى المهام، يعيد التطبيق حساب نسبة الإنجاز.

إذا احتوت الخطة على خمس مهام واكتملت مهمتان، فإن نسبة الإنجاز تكون:

**Progress = (2 ÷ 5) × 100 = 40%**

إذا لم تحتوِ الخطة على أي مهام، يجب أن تكون نسبة الإنجاز `0%`.

## 5. متطلبات التطبيق — Application Requirements

تحدد المتطلبات الوظائف الأساسية التي يجب أن يوفرها النظام.

### 5.1 إدارة المستخدمين — Authentication

- إنشاء حساب جديد.
- تسجيل الدخول والخروج.
- ربط البيانات بالمستخدم المصادق عليه.
- منع الوصول غير المصرح به إلى الصفحات والبيانات الخاصة.

تُدار المصادقة باستخدام **Supabase Auth**.

### 5.2 إدارة الخطط — Plan Management

يستطيع المستخدم:

- إنشاء خطة.
- استعراض خططه.
- عرض تفاصيل خطة.
- تعديل معلومات الخطة.
- حذف خطة.

### 5.3 إدارة المهام — Task Management

يستطيع المستخدم:

- إضافة مهمة إلى خطة.
- استعراض المهام.
- تعديل المهمة.
- حذف المهمة.
- تحديد أولوية المهمة.
- تحديث حالة التنفيذ.

### 5.4 إدارة الأولويات — Priority Management

تدعم المهام القيم التالية:

- `High`
- `Medium`
- `Low`

### 5.5 حالات التنفيذ — Status Management

تدعم المهام الحالات التالية:

- `To Do`: لم يبدأ التنفيذ.
- `In Progress`: قيد التنفيذ.
- `Done`: اكتمل التنفيذ.

يجب أن تتوافق القيم المستخدمة في التطبيق مع القيود المحددة في قاعدة البيانات.

### 5.6 متابعة التقدم — Progress Tracking

يحسب التطبيق نسبة الإنجاز بناءً على عدد المهام المكتملة:

**Progress Percentage = (Completed Tasks ÷ Total Tasks) × 100**

يجب إعادة حساب النسبة عند تغيير حالة إحدى المهام، مع التعامل بصورة صحيحة مع الخطط التي لا تحتوي على مهام.

### 5.7 حفظ البيانات — Data Persistence

يجب أن تبقى الخطط والمهام محفوظة في قاعدة البيانات بعد تحديث الصفحة أو تسجيل الخروج ثم تسجيل الدخول مجددًا.

### 5.8 عزل البيانات — User Data Isolation

يجب أن يتمكن كل مستخدم من إدارة بياناته الخاصة فقط.

تُفرض هذه القيود على مستوى قاعدة البيانات باستخدام `Row Level Security (RLS)`، وليس اعتمادًا على إخفاء البيانات في الواجهة فقط.

## 6. صفحات التطبيق — Application Pages

تتكون النسخة الأولى من الصفحات التالية:

### 6.1 الصفحة الرئيسية — Landing Page

تعرض فكرة التطبيق والقيمة التي يقدمها، وتتيح الانتقال إلى التسجيل أو تسجيل الدخول.

### 6.2 صفحات المصادقة — Authentication Pages

تتيح للمستخدم إنشاء حساب أو تسجيل الدخول.

### 6.3 صفحة الخطط — My Plans

تعرض الخطط الخاصة بالمستخدم الحالي، وتتيح إنشاء خطة جديدة أو فتح خطة موجودة.

### 6.4 صفحة إنشاء الخطة وتعديلها — Create / Edit Plan

تتيح إدخال بيانات الخطة أو تعديلها، بما يشمل:

- `title`
- `description`
- `goal`
- `deadline`

يمكن دعم `deliverables` و`next_step` إذا كانت هذه الحقول متاحة في واجهة التطبيق المنفذة.

### 6.5 صفحة تفاصيل الخطة — Plan Details

تعرض تفاصيل الخطة والمهام المرتبطة بها، وتتيح إدارة المهام ومتابعة تقدم التنفيذ.

## 7. التقنيات والمفاهيم — Technology Stack

### 7.1 التقنيات المستخدمة

| التقنية | الاستخدام |
|---|---|
| Lovable | بناء التطبيق باستخدام AI App Builder |
| Supabase Auth | المصادقة وإدارة حسابات المستخدمين |
| Supabase PostgreSQL | تخزين الخطط والمهام |
| Supabase RLS | التحكم في الوصول إلى البيانات |
| GitHub | توثيق المشروع وإدارة ملفاته وإصداراته |

### 7.2 المفاهيم الهندسية المستخدمة

**AI App Builder:** أداة تستخدم الذكاء الاصطناعي للمساعدة في بناء التطبيقات انطلاقًا من وصف المتطلبات.

**Frontend:** الجزء الذي يتفاعل معه المستخدم، مثل الصفحات والنماذج والأزرار.

**Backend:** الجزء المسؤول عن منطق التطبيق والتعامل مع الخدمات والبيانات.

**Database:** نظام تخزين البيانات بصورة منظمة.

**Authentication:** التحقق من هوية المستخدم.

**CRUD:** العمليات الأساسية للتعامل مع البيانات: Create, Read, Update, Delete.

**Relational Database:** قاعدة بيانات تربط الجداول باستخدام العلاقات والمفاتيح.

**Data Persistence:** استمرار حفظ البيانات وإمكانية الوصول إليها لاحقًا.

**Row Level Security (RLS):** سياسات تحدد السجلات التي يستطيع المستخدم الوصول إليها.

**Responsive Design:** تصميم يتكيف مع أحجام الشاشات المختلفة.

**Data Integrity:** الحفاظ على صحة البيانات واتساقها باستخدام القيود والعلاقات والتحقق من القيم.

## 8. تصميم النظام — System Design

يعتمد النظام على العلاقة التالية:

**User → Plans → Tasks**

- يمتلك المستخدم عدة خطط.
- تحتوي الخطة على عدة مهام.
- تنتمي كل مهمة إلى خطة واحدة.
- يجب أن يكون مالك المهمة هو نفسه مالك الخطة.
- يؤدي حذف الخطة إلى حذف المهام المرتبطة بها.

### 8.1 جدول الخطط — `plans`

يخزّن بيانات الخطط.

| الحقل | الوصف |
|---|---|
| `id` | المعرّف الفريد للخطة |
| `user_id` | معرّف المستخدم المالك |
| `title` | عنوان الخطة |
| `description` | وصف الخطة |
| `goal` | الهدف أو النتيجة المطلوبة |
| `deadline` | الموعد النهائي الاختياري |
| `deliverables` | المخرجات المتوقعة بصيغة JSONB |
| `next_step` | الخطوة التالية الاختيارية |
| `created_at` | تاريخ الإنشاء |
| `updated_at` | تاريخ آخر تحديث |

### 8.2 جدول المهام — `plan_tasks`

يخزّن المهام التابعة للخطط.

| الحقل | الوصف |
|---|---|
| `id` | المعرّف الفريد للمهمة |
| `plan_id` | معرّف الخطة المرتبطة بالمهمة |
| `user_id` | معرّف المستخدم المالك |
| `title` | عنوان المهمة |
| `description` | وصف المهمة الاختياري |
| `priority` | أولوية المهمة |
| `status` | حالة التنفيذ |
| `sort_order` | ترتيب المهمة |
| `created_at` | تاريخ إنشاء المهمة |

### 8.3 سلامة البيانات — Data Integrity

يجب أن يضمن تصميم قاعدة البيانات:

- وجود مفتاح أساسي فريد لكل سجل.
- ارتباط كل خطة بمستخدم.
- ارتباط كل مهمة بخطة موجودة.
- تطابق مالك المهمة مع مالك الخطة.
- قبول قيم الأولوية والحالة المسموح بها فقط.
- حذف المهام التابعة عند حذف الخطة.
- استخدام قيم افتراضية مناسبة.
- توفير الفهارس المناسبة للاستعلامات المتكررة.

للاطلاع على تفاصيل الجداول والعلاقات والقيود وسياسات الأمان وكود SQL، راجعي ملف قاعدة البيانات:

## 9. الأمان — Security Design

الأمان جزء أساسي من تصميم TaskBridge.

### 9.1 المصادقة

تُستخدم Supabase Auth لإدارة حسابات المستخدمين والتحقق من هويتهم.

### 9.2 سياسات الوصول

يجب تفعيل `Row Level Security (RLS)` على جدولي `plans` و`plan_tasks`.

تُضبط السياسات بحيث يستطيع المستخدم الوصول إلى السجلات التي يملكها فقط.

### 9.3 حماية العلاقات

يجب منع المستخدم من إنشاء مهمة مرتبطة بخطة لا يملكها، أو تعديل بيانات تخص مستخدمًا آخر.

### 9.4 حماية المفاتيح

يُمنع وضع مفتاح `service_role` في كود الواجهة الأمامية أو رفعه إلى مستودع GitHub العام.

يجب استخدام مفتاح العميل المناسب مع تطبيق سياسات RLS بصورة صحيحة.

### 9.5 التحقق من الأمان

يجب اختبار الصلاحيات باستخدام حسابين مختلفين على الأقل، والتحقق من عدم قدرة أحدهما على الوصول إلى بيانات الآخر أو تعديلها أو حذفها.

**ملاحظة:** وجود سياسات RLS لا يثبت وحده أن التطبيق آمن؛ يجب اختبار سلوك قاعدة البيانات والتطبيق فعليًا.

## 11. الاختبارات — Testing Checklist

يجب اختبار التطبيق الفعلي قبل اعتباره مكتملًا.

### 11.1 المصادقة

- [ ] يستطيع المستخدم إنشاء حساب.
- [ ] يستطيع المستخدم تسجيل الدخول.
- [ ] يستطيع المستخدم تسجيل الخروج.
- [ ] تتطلب الصفحات الخاصة المصادقة المناسبة.

### 11.2 إدارة الخطط

- [ ] يستطيع المستخدم إنشاء خطة.
- [ ] يستطيع المستخدم استعراض خططه.
- [ ] يستطيع المستخدم تعديل خطة.
- [ ] يستطيع المستخدم حذف خطة.

### 11.3 إدارة المهام

- [ ] يستطيع المستخدم إضافة مهمة.
- [ ] يستطيع المستخدم تعديل مهمة.
- [ ] يستطيع المستخدم حذف مهمة.
- [ ] يستطيع المستخدم تغيير الأولوية.
- [ ] يستطيع المستخدم تغيير الحالة.

### 11.4 التقدم وحفظ البيانات

- [ ] تتغير نسبة الإنجاز عند إكمال مهمة.
- [ ] تتغير نسبة الإنجاز عند تغيير حالة مهمة مكتملة.
- [ ] تظهر نسبة الإنجاز 0% عندما لا تحتوي الخطة على مهام.
- [ ] تبقى الخطط محفوظة بعد تحديث الصفحة.
- [ ] تبقى المهام محفوظة بعد تحديث الصفحة.
- [ ] تبقى التعديلات محفوظة بعد تسجيل الخروج والدخول مجددًا.

### 11.5 الأمان

- [ ] لا يستطيع المستخدم A قراءة خطط المستخدم B.
- [ ] لا يستطيع المستخدم A تعديل خطط المستخدم B أو حذفها.
- [ ] لا يستطيع المستخدم A قراءة مهام المستخدم B أو تعديلها أو حذفها.
- [ ] لا يستطيع المستخدم إنشاء مهمة مرتبطة بخطة يملكها مستخدم آخر.
- [ ] يؤدي حذف الخطة إلى حذف المهام المرتبطة بها.

**لا تُعد أي وظيفة مختبرة حتى يتم التحقق من سلوكها الفعلي.**

## 15. المبدأ الهندسي — Engineering Principle

> **Build the System, Not the Screen.**
>
> ابنِ النظام، لا الواجهة فقط.

بناء التطبيق لا يعني إنشاء واجهة جذابة فحسب، بل يتطلب فهم المشكلة، وتصميم البيانات والعلاقات بينها، وتحديد سلوك النظام، وحماية المعلومات، والتحقق من صحة الوظائف.

تساعد أدوات AI App Builders على تسريع التنفيذ، لكنها لا تلغي مسؤولية المهندس عن فهم النظام الناتج وتوجيهه وتقييمه وتحسينه.

المهندس لا يكتفي بأن يرى التطبيق يعمل، بل يتحقق من أن:

- التطبيق يعالج المشكلة المطلوبة.
- البيانات منظمة والعلاقات صحيحة.
- الوظائف تعمل كما هو متوقع.
- البيانات تُحفظ بصورة صحيحة.
- صلاحيات الوصول مضبوطة.
- الأخطاء والحالات غير المتوقعة تُعالج بصورة مناسبة.

**We don't teach them to build what AI can build. We teach them to understand, design, direct, evaluate, and improve what AI builds.**
